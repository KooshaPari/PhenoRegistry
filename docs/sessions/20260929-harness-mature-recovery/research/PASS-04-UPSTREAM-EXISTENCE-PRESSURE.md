# SOTA pass 4 — current upstream pressure on the existence gate

Retrieved 2026-09-29. Primary source/control: current 1jehuang/jcode repository and releases, plus frozen owned sources. This pass changes the KCode alternative stack materially.

## Current upstream jcode is not the frozen fork's historical baseline

Current upstream release v0.89.0 (released 2026-09-28) documents built-in voice input, applets, persistent account pools, deferred MCP tool loading, daemon KV-cache miss reporting, SDK SSH identity/pinned-host-key support, and fixes to daemon reload readiness. Its current repository documents persistent server/client workflows, swarm coordination, browser automation, Rust/TypeScript SDKs and multi-session/server-owned session architecture.

The frozen KCode master is version 0.85.1-k1.1.1. A material owned divergent branch carries upstream-style 0.88.0. Therefore any existence claim based on KCode versus an older upstream is invalid.

## Revised counterfactual

If KCode disappeared today, the strongest realistic first alternative is **current upstream jcode 0.89.x + a thin owned policy/evidence/runtime-identity adapter + only proven retained fork patches**. This is stronger than the earlier generic “upstream jcode” placeholder.

Before preserving a deep fork, produce a retained-patch ledger:
- obligation/user intent;
- fork implementation commit(s);
- current upstream equivalent or absence;
- behavioral difference under a matched test;
- migration cost;
- maintenance cost/risk;
- disposition: upstream already solves / contribute upstream / thin adapter / retained patch / reject.

Fork survival cannot be justified by server/client, swarm, session persistence, browser, SDK, OAuth/provider breadth, memory, or resource-efficiency claims alone because current upstream already substantially occupies those surfaces.

## Candidate fork differentiation under attack

Potential surviving owned differentiation is narrower:
1. exact runtime/evidence identity integrated with the user's MACE/traceability system;
2. provider/subscription routes or harness semantics demonstrably absent upstream;
3. native Windows/Pine compatibility obligations beyond current upstream behavior;
4. integrations with owned PhenoShared/Helios/Tracera/AgilePlus capabilities;
5. specific accepted fork patches whose behavior is not upstreamed.

Each remains unverified until the retained-patch ledger and matched experiments exist.

## HeliosLite pressure

Current upstream Forgecode already provides interactive, one-shot and shell-plugin modes, broad provider configuration, MCP, semantic workspace search, provider credential management and multi-agent workflow use. Generic provider breadth, MCP and CLI modes therefore remain commodity/contested. Historical fork coexistence intent gives a legitimate identity/isolation obligation if HeliosLite survives, not a reason for survival by itself.

## Decision consequence

Do not freeze either owned fork's architecture around its current implementation. Prefer the smallest maintained delta over a healthy upstream that preserves accepted differentiation. A deep fork must earn its carrying cost with measured behavior that cannot be obtained by configuration, adapter, upstream contribution or a small patch stack.

No winner is declared. Required next evidence is source-level retained-patch diff classification and matched behavior/cost experiments.
