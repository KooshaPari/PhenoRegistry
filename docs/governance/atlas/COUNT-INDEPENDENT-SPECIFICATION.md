# Repo-by-repo specification: counts are outputs only

**User correction — September 29, 2026. Supersedes numerical expectations in the earlier chat handoff, ZIP/PDF instructions and generated catalogue descriptions.**

Numbers mentioned conversationally are not requirement targets, minimums, maximums, estimates to fit, quotas or expected ranges. Do not impose equal domains/features/requirements across repositories or multiply generic dimensions to reach or exceed a number. Do not stop, pad, truncate, split or merge to satisfy a count. A larger number is not a substitute for comprehensive coverage.

## Required outcome

Describe the most comprehensive presently knowable mature product and organize it into meaningful capabilities/features/sub-features, independently falsifiable obligations, viable-stage projections, real journeys, work surfaces, growth dispositions and concrete verification intent. The large backlog is intentional. Do not narrow the product to the current MVP or invent adjacent scope for volume.

## Method

Reconcile accepted user intent with product definitions, source-native requirements, ADRs, interfaces, domain/state models, human and machine journeys, supported components, data persistence, concurrency, failure/recovery behavior, integrations, tests and known limitations. Record exact source identities and reviewed extent. Existing code is descriptive evidence, not automatically normative intent. Inferences require rationale and proposal status. Preserve prior requirements and historical decisions with explicit crosswalks.

Use semantic decomposition: split independent observable obligations; merge duplicates without losing meaning. A test permutation is not automatically an FR. A shared constraint should be linked to its applicable features instead of copied for count inflation. Uniform prose such as 'implement X correctly' is a review prompt, not a specification. Templates may standardize fields, not manufacture substance.

Derive stages from coherent usable outcomes and dependency closure. Array order, an arbitrary percentage or a fixed number per domain cannot determine applicability. Distinguish scaffold/primitives from closed features and real journeys. Stub breadth behind stable boundaries and implement a real spine; compatibility and survivability require support or labelled estimates.

Design concrete acceptance/oracle cases now, including actual inputs/preconditions, expected results, counterexamples, fixture/environment/reset needs and evidence binding. Mass product-test generation remains deferred. Reserved test IDs and generic oracle sentences do not establish readiness.

Review source coverage, contradictory intent, missing behaviors, duplicates, hierarchy, stage/journey links and implementation locations before declaring the specification pass complete. Independent semantic review and structural validation answer different questions. A parse or count check does not prove comprehensiveness. Record unfinished coverage honestly when work is partial. Counts can then summarize reviewed artifacts, never govern generation or acceptance.

Those claims are withdrawn. Original drafts remain in their repository histories; they are not accepted baselines or grading denominators. Source-native requirements are not cancelled.
