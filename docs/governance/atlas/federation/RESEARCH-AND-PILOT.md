# Research and comparative proof

## Claim being tested

Hypothesis: reciprocal semantic composition reduces setup/context-switching/maintenance burden while meeting the standalone products' critical correctness, privacy, performance and accessibility obligations. The mechanism is typed capability reuse plus host-relative surfaces and scoped state—not a new launcher or visual skin.

Competing hypotheses: contextual deep links are sufficient; a conventional plugin host is simpler; a pre-integrated suite is better; pair-specific adapters are cheaper for the small real integration graph; federation introduces too much versioning and security complexity. Test these before claiming an ecosystem moat.

## Baselines

For the same user job, compare (A) separate qualified apps plus documented manual integration, (B) deep-link/context handoff, (C) one conventional plugin-host composition, (D) proposed reciprocal federation, and where relevant (E) an established integrated suite. Use primary-source mechanisms in SOURCES as implementation references, not as fictitious drop-in competing products.

This amendment is not another 25-product market survey. Existing per-product SOTA longlists remain in force. Here the question is whether this particular interaction/composition mechanism improves their real common workflows. Do not pad the reference list with unrelated projects to reach a count.

## First witness: Tracera + AgilePlus

Each app must work independently on the selected supported profile. Bind one real product/capability/work item. Run install A then B and B then A; open each as primary; execute a real scoped edit with an actual receipt; navigate to the same object from both; open both at once; terminate and restart a provider; revoke write access; update one app; detach/uninstall B; prove A's base workflow and both apps' retained data.

Use a nontrivial seeded project with known missing requirements, conflicting changes and private data that another context must not see. No synthetic dashboard, placeholder backend or manual database copy can establish reciprocal federation.

## Second and nested witnesses

BytePort + ShareCLI is a suggested distinct pair: deploy/operate from BytePort while ShareCLI offers scoped process/control surfaces, then inspect the same authorized workload from ShareCLI while BytePort provides deployment context. Qualification must retain ownership and dangerous-action boundaries; two UIs cannot initiate duplicate retries or unapproved rollbacks.

For a nested composition, host a reduced composite inside an existing approved shell or App Center view. Check that it exposes only intentional capabilities, not all child secrets/settings. Stop recursive UI embedding and event loops. Choose actual runnable pairs; these suggestions do not reassign a repository or authorize source movement.

## Measurements

Predeclare exact hardware/OS/builds, isolated environments, task corpus, user expertise, permissions and failure schedule. Measure setup actions and failure rate, manual identity/path/credential copying, context-switch count, task completion/error rate, provider diagnostic quality, install/update/detach time, retained-data integrity, command latency distribution, startup, memory, GPU/CPU use and load interference.

Assess developer ergonomics too: effort to add a provider and a second host, host-specific code versus reused domain logic, change amplification, number of pair-specific adapters, version compatibility burden, documentation ambiguity, debugging time and external-author onboarding. Count patches and duplicated policy rather than celebrating framework LOC.

Visual/interaction review should use qualified native output and assistive/keyboard journeys. Blind task-based review where practical is preferable to awarding a perfect score because the author chose attractive screenshots. Retain uncertainty, failed runs and exact integration-tier limitations. Benchmarks are unexecuted until native receipts exist.

## Required adversarial matrix

Include no-peer, unsupported-peer, ambiguous-provider, mismatched-version, untrusted-manifest, revoked-scope, two tenants, slow/crashing provider, no network, partial install, unknown previous operation outcome, concurrent hosts, hot update with in-flight action, broker restart, uninstall with another consumer, URI injection, context substitution, and event-loop storms. Use pairwise configurations for routine breadth but fully test critical boundaries. Pairwise coverage is not proof of every higher-order interaction.

The previous independent 85%+ suite obligations and stronger accepted floors remain. Critical federation invariants require complete evidence; aggregate standalone coverage cannot hide untested composed paths. A schema pass is not permission, an attestation is not correctness, and a screenshot is not a successful interaction.

## Graduation

Graduate a binding profile only after standalone parity, both declared directions, the lifecycle/failure matrix and the user's native experience review succeed. Record any disadvantage and its audience. If the mechanism is not beneficial, retain a simpler deep-link or conventional plugin solution and preserve the unfulfilled long-term intent as research. Do not market an automatic union of arbitrary third-party applications.
