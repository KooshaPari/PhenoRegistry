Keep one owner chat per current non-zz subject. Refresh actual role, identity and lease; do not reactivate obsolete ten-seat/pair instructions. Independent verification remains required, but writing an approval string does not establish approval.

The following eight work packages are proposed and unestimated until the actual subject, source paths, environment and authority are bound. Full requirements, negative controls, rollback and permission prerequisites are in `proof/work-packages.json` and specs/013 through specs/016.

## WP-PROOF-13-1 — Capability-first composition: contract and first positive path

Bind one host command to a real owned or external provider through the least-cost valid boundary, with no peer-UI mount. Record provider/consumer contracts, shared object identity and before/after behavior.

**Decisive counterexample:** A valid in-process provider is not forced through an unnecessary network layer.

**Dependency:** No universal prerequisite; local scope/permissions still required.

## WP-PROOF-13-2 — Capability-first composition: negative controls and qualified consumer

Run the same contract with the provider absent, failed, revoked and replaced; add a second compatible consumer and prove one authoritative result with no duplicate mutation or data copy.

**Decisive counterexample:** Mocked provider success cannot satisfy a required live integration.

**Dependency:** WP-PROOF-13-1.

## WP-PROOF-14-1 — Agent bridge and graphical proof: contract and first positive path

**Dependency:** No universal prerequisite; local scope/permissions still required.

## WP-PROOF-14-2 — Agent bridge and graphical proof: negative controls and qualified consumer

**Dependency:** WP-PROOF-14-1.

## WP-PROOF-15-1 — Canonical design and complete artifact traceability: contract and first positive path

Canonicalize one editable UI/flow or scene design with populated/empty/error/recovery states and fixture data. Keep proposals and approval evidence separate; link the actual implementation and capture.

## WP-PROOF-15-2 — Canonical design and complete artifact traceability: negative controls and qualified consumer

**Decisive counterexample:** Dropping a hard requirement to improve the percentage is visible and needs authorization.

**Dependency:** WP-PROOF-15-1.

## WP-PROOF-16-1 — Evidence-bound numeric product grading: contract and first positive path

Bind the existing rubric owner to one frozen scope/profile. Adapt native evidence into typed scored obligations, compute category weights and a literal percentage/letter, and display missing weight and mandatory gates.

**Decisive counterexample:** A high numeric grade with a failed critical invariant remains BLOCKED.

## WP-PROOF-16-2 — Evidence-bound numeric product grading: negative controls and qualified consumer

Adversarially test grade dilution, stale/wrong-build receipts, missing media, synthetic/live mismatch and failing critical checks. Compare the computed grade with independently inspected outcomes and qualify actual producer/oracle boundaries.

**Decisive counterexample:** No invented acronym or new registry becomes authority from this amendment.

**Dependency:** WP-PROOF-16-1.

## First integration wave

Choose one owned-game witness (Civis), one permitted gray-box witness (Dino or WorldSphereMod), and one ordinary GUI or CLI consumer. Do not start 24 new bridge implementations. Shared capture/action/evidence interfaces have an owner; engine/platform-specific adapters remain with their products. No product waits for a universal atlas or App Center.

For each witness: define intent and a design fixture; capture one actual user-path action and its state/pixel outcome; seed a known-bad counterpart; bind the receipts to a frozen score rubric; then compare the claimed grade with independently inspected results. A valid transport packet, screenshot filename or scoring-schema pass is not this integration outcome.

A second wave broadens visual classes, design states, reverse lifecycle cases and support profiles. Continue safe independent work while external blockers retain exact owners and wakeup actions. Existing native run and independent assurance requirements remain in force. No fabricated percentages or arbitrary 100% completion labels arise from this package.
