# Authority correction — BytePort ADR-001 provider strategy

Date: 2026-09-30.

Conversation recovery was queried specifically for direct user authority on:
- AWS-primary provider strategy;
- NVMS/odin.nvms;
- CLI-primary;
- portfolio generation/publication;
- desktop/Tauri.

Recovered direct user conversation confirms BytePort/NVMS were active project concepts in April 2026, but did not recover a direct user statement adopting the detailed AWS-primary/package-tree architecture. Earlier assistant descriptions of BytePort as Git→AWS→portfolio are assistant-authored and therefore not user intent.

## Classification

### Better corroborated mature product intent
- Git/repository to deployed product;
- productization/portfolio projection/publication;
- manifest/declarative deployment concept;
- CLI importance/primary accepted ADR;
- multiple human/machine projections.

### Accepted-design evidence, not immutable user intent
- AWS as primary v1 cloud;
- exact Go/Cobra/Gin/AWS package decomposition;
- exact package paths in ADR-001;
- LLM backend choices;
- historical numeric performance targets.

### Current architecture pressure
Current recovery favors provider/runtime adapters and a capability-based BuildEngine. NanoVMS is one runtime boundary candidate; AWS may remain an adapter/target rather than product identity.

## Decision consequence

Do not freeze AWS-primary as the mature BytePort identity solely because ADR-001 is Accepted.

Provider strategy remains:
- adapter-based;
- validated against current alternatives and actual product differentiation;
- capable of AWS support where justified;
- not coupled to obsolete package paths.

The accepted ADR still contributes semantic obligations where independently corroborated, but its provider-specific choices remain revisable architecture.
