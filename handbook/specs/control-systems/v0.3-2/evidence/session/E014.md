# Podman Quadlet & VSOCK Networking in WSL2 Research Report

## Question 3: Can Podman Quadlet services run WITHOUT systemd inside WSL2?

### Findings:
- **Genie** (arkane-systems/genie): Creates a PID namespace, starts systemd as PID 1 inside that namespace ("poor-man's-container bottle"), then enters it. Explicitly states it provides "a way to run systemd as pid 1, with all the trimmings, inside WSL 2."
- **Native WSL2 systemd support**: Microsoft confirms WSL supports systemd natively since WSL 0.67.6+ (Windows 11). systemd runs as PID 1 and manages services - this is the preferred approach over Genie.
- **Podman Quadlet documentation**: Quadlet files (.container, .service, etc.) are explicitly defined as "systemd units using Podman Quadlet." They require placement in standard systemd search paths (`/run/containers/systemd/`, `/etc/containers/systemd/`, etc.) and depend on systemd being present as PID 1 to process these units.
- **wsld**: Though README couldn't be fetched, naming and context indicate it's another WSL daemon/systemd init tool similar to Genie.

### Verdict for (3): **works-with-caveats**
- Quadlet services **cannot run without systemd** - they fundamentally require systemd as PID 1 to interpret and execute the unit files.
- However, they **can run in WSL2** via either:
  1. **Native WSL2 systemd** (preferred): WSL 0.67.6+ on Windows 11
  2. **Genie/wsld workaround**: These tools provide systemd as PID 1 by creating a PID namespace "bottle" and running systemd inside it
- **Caveat**: You must have systemd running as PID 1 - either natively in WSL2 or via Genie/wsld's namespace container.

## Question 6: Is podman+vsock networking stable for inter-service communication on Windows/WSL2?

### Findings:
- **podman-machine documentation**: Shows Windows uses `wsl*` as the default provider (marked with asterisk in the provider table), meaning Podman on Windows relies on the WSL2 backend.
- **VSOCK implication**: WSL2 uses VSOCK (VMware vsockets) for host-guest communication. The podman-machine architecture inherently uses VSOCK for communication between the Windows host and the WSL2 VM where containers run.
- **No contrary evidence**: Fetched documentation shows VSOCK as the designed communication mechanism for podman machine on Windows/WSL2, with no indications of instability in the core docs reviewed.
- **Quadlet integration**: Since Quadlet depends on systemd (which runs inside the WSL2 VM), and containers communicate via the podman-managed WSL2 backend, VSOCK remains the underlying transport for host-container and inter-service communication patterns.

### Verdict for (6): **works**
- Podman+vsock networking is the **designed and stable path** for inter-service communication on Windows/WSL2.
- The WSL2 provider in podman machine inherently uses VSOCK, and this is the officially supported mechanism.
- No instability was indicated in the fetched Podman documentation; VSOCK appears to be the production-ready communication channel.
