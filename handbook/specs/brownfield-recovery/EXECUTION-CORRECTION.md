# Execution correction: portfolio outcomes, not isolated repair completion

Use this as a correction to the existing portfolio assignment. Do not restart the portfolio audit or replace stronger local documentation, provenance, task formats, or evidence tooling. Preserve completed work and reevaluate only changed or insufficient evidence.

## Mission and authority

The parent outcome remains: evidence-backed polyrepo shaping; approved absorption, decomposition, integration or retention; then a usable, stable, verified target release or an accepted non-product terminal state. A narrow repair is a child deliverable, not the entire assignment.

Current explicit operator decisions and authorizations control. This correction does not grant new remote-write, merge, publication, archive, repository-creation, cross-repository-write, credential, security-policy, or history-rewrite authority. Existing scoped repair/commit/push/PR permissions remain valid. A delegated coordinator may decide within its documented remit; genuine operator-reserved decisions remain reserved.

## Coordinator responsibilities

1. For each active repository, attach an explicit desired outcome: retain/refocus, integrate, absorb, decompose, incubate, reference, archive/retire, or unresolved. Bind it to the accepted decision and immutable baseline, or keep it visibly proposed. Do not silently adopt a historical register recommendation.
2. Define a bounded target release, migration, or incubation experiment, its capability scope, acceptance checks, and closure owner. Do not demand completion of the repository's entire imagined lifetime roadmap.
3. Maintain a before/transition/after map. Every source capability needs a disposition and every required integration needs an owner. File movement or a working redirect is not migration parity.
4. Assign migration work around source-target-consumer dependencies, not merely adjacent names on the portfolio list. Cross-worker changes need coordinated source and destination work packages, compatible contract versions, write leases and a joint verifier. Preserve exclusive write scope; arrange read-only dependency inspection within authorized access.
5. Dispatch the exact decision, target, next work package, dependencies, permission envelope and acceptance evidence to each worker. Do not use 'read everything in Downloads' as the task contract. Name the authoritative files and revisions; other documents are supporting evidence.
6. Keep parent outcome responsibility after delegation. A handoff does not erase residual work. Every external blocker or authority request needs an ID, named owner, exact action, affected gates, and wakeup/recheck condition. Receiving ownership must be acknowledged before an item disappears from a queue.
7. Track portfolio-wide active work, review backlog and hardware/CI contention. Three repositories per worker is a local cap, not a global cap. Park genuinely blocked work without calling it complete; use released capacity for another ready item.

## Worker responsibilities

For each assigned repository, reconcile the latest applicable decision and target, then emit a concise outcome-gap record covering role, capability scope, migration/consumer obligations, tests, hosted checks, installation/release, pilot or justified equivalent, and remaining acceptance items.

Continue through ready authorized work that advances that outcome. Keep individual PRs narrow. Inherited in-repository defects that block the assigned target stay in the outcome backlog; split them into follow-on work packages/PRs rather than declaring them somebody else's problem because they predate your diff. An additional work package is not automatically an additional permission request when its actions already fit the granted scope.

When a repair changes public contracts, supported versions, security policy, shared upstream workflows, or another owner's files, identify the actual decision or authority needed. Do not infer permission to expand the product or bypass controls. Reproduce baseline/head behavior with comparable inputs before labeling a failure inherited.

Classify outstanding work independently by origin and by owner: introduced defect; inherited local defect; shared-source defect; external service/credential blocker; product decision; review/merge/release action. Unsupported attribution remains unknown. Unavailable tools and credentials are not successful checks.

Do not start another generic docs pass when valid evidence already exists. Implementation findings may require a focused spec, contract or test amendment; preserve links to the original intent and record the change.

## Reporting and stop rules

Report these separately using existing task/gate vocabulary where possible:
- Child work-package status.
- PR review readiness and actual required-check status.
- Integration/default-branch status.
- Bounded repository-target status.
- Migration/consumer status.
- Portfolio-outcome status.

An open PR is not integration. Review readiness is not merge readiness. Evidence-file counts are not acceptance. A blocked repository is not closed. A legitimately completed bounded task may be closed while its parent remains open, provided residual work stays assigned and visible.

Only report repository-target closure when all applicable acceptance obligations for its chosen role and target are evidenced, reviewed as required, and accepted by the designated authority. A valid archive/reference outcome need not become a fully modernized product; an incubator needs its agreed experiment/decision, not a fabricated production graduation.

When awaiting review or an external action, continue other safe ready work inside the authorization envelope. If none remains, return a blocker packet and release the execution slot; do not repeatedly offer cosmetic menus or request the next batch while hiding an unfinished parent outcome.
