# Catalog, profiles and measurement bindings

The release has 1,080 authored candidate entries across 108 pillars and 18 domains. That is a count of this release, not a recovered historical count or independently adjudicated count of unique controls. Domain Markdown is generated navigation; `catalog/catalog.json` is the catalog authority for this release.

## Selection procedure

Identify product form, real capabilities, beneficiary slice, platform, exposure, persistence, distribution channel and target maturity. Choose a profile as a shortlist, then inspect capability-created obligations across omitted domains. A library may require authentication or privacy; a graphical product may have no hosted deployment. Product form never establishes a blanket exemption.

Create scoped instances with unique IDs and obligation keys. Select weights and gates before viewing the score. Record unresolved applicability instead of convenient exclusions. Preserve known parent obligations when narrowing the current task. Distinguish a bounded assessment from full-catalog discovery; both may proceed concurrently.

A criterion may apply to several packages or platforms. Those are instances, not new conceptual criteria. Cross-framework aliases and cross-cutting duplicate obligations must not receive independent credit. The reference kernel conservatively rejects repeated obligation keys; a richer grouping reducer must preserve fixed group budgets and prove its semantics before adoption.

## Activation checklist

For each selected predicate, bind the exact subject and relevant source/artifact/environment, an observation population or journey, expected behavior, units and thresholds or semantic anchors, permitted effects, resource limit, fixtures, positive and negative controls, evidence requirements and invalidators. Link qualification receipts. A procedure without these details is a visible measurement-design task, not a license to make up a score.

Use the catalog's method as a starting point, not an authority to execute arbitrary repository instructions. A qualified structural parser proves structure; it does not prove runtime behavior. A screenshot proves a rendered state; it does not prove task completion. A model-generated review may support a scoped semantic judgment when properly anchored but must abstain when evidence is inadequate.

## Levels of automation

`PROCEDURE_ONLY`: an agent can follow the method but no executable adapter is supplied by the catalog. `IMPLEMENTED_UNQUALIFIED`: local code exists but positive/negative testing is incomplete. `QUALIFIED_SCOPED`: the instrument has actual receipts covering named inputs and failure classes. `OPERATED`: the qualified path has observed ongoing behavior under a stated environment.

All shipped catalog entries are PROCEDURE_ONLY / UNQUALIFIED. The separate reference kernel has tests for its own reduction and validation behavior; that does not qualify 1,080 product adapters. Promotion into an operational assignment must remain evidence-backed.

## Backlog routing

Implementation gaps → bounded repair. Verification gaps → instrument or test. Requirement gaps → assignment review. Research gaps → evidence acquisition. Opportunities → explicit acceptance or experiment. Contradictions → adjudication or disconfirming test. Obsolete capabilities → consumer and custody analysis. Measurement defects → qualified evaluator revision. Provenance gaps → recovery, not invented history.
