# File-first operating procedure

## 0. Enter an existing work context

Locate the actual subject, owner-held audit paths, current source/BOM, standing mandate, work claims, prior assessment and checkpoint. Do not overwrite dirty work or create another portfolio registry. Record access limits. An inability to locate past intent becomes a provenance finding, not a reason to manufacture a human instruction.

## 1. Recover or derive a bounded outcome

State a beneficiary or actual consuming system, parent intent, problem hypothesis, expected effect, alternatives, non-goals and refutation condition. Decide whether the next useful unit is a repair, delivery slice, discovery pass or experiment. Accept the assignment only under actual authority.

## 2. Select scope and build the grader

Use a profile to navigate relevant criteria. Bind specific predicates and non-compensating gates. Include preservation of existing required behavior. Qualify the important instruments with valid and invalid controls. Missing environment, permission, expert evaluation and product implementation are distinct blockers.

## 3. Freeze and observe

Lock the epoch and record subject, catalog, evaluator and environment identities. Execute the cheapest adequate existing checks: parsers and linters for structure, tests and consumer programs for behavior, anchored semantic review for judgment, and real observations for value. Record commands/actions, assertions, raw evidence digests, timing and inspected scope. A command's name or configured workflow is not evidence it ran.

## 4. Interpret before writing more code

Classify findings. Compare implementation fault, invalid requirement, broken oracle, environment failure, permission boundary, missing research and wrong problem. Route each to its actual owner and correct next-action type. Do not turn every possible enhancement into accepted debt.

## 5. Execute bounded work

Use an isolated authorized branch/worktree or sandbox. Keep work claims and cumulative resources valid. Favor critical blockers, real end-to-end outcomes and information-rich experiments over easy point gains. Record meaningful failed attempts with reproducible evidence.

## 6. Verify and integrate

Verify the actual candidate with acceptance inputs the builder cannot silently weaken. Re-run invalidated evidence. Distinguish local candidate success, integration acceptance, release verification, publication and operated behavior. No mode grants a right to merge, publish or delete unless the mandate already does. Ordinary delegated actions do not require repeated sponsor approval.

## 7. Commit the record and checkpoint

Record the evaluated subject S; store the report later at R; register references later at L when available. Make pending or blocked registration explicit. Preserve findings, decisions, evidence and a compact restart packet. A fresh worker must locate the accepted baseline, useful candidate state, prior failed hypotheses, remaining resources and next discriminating action.

## 8. Return a useful result

Return exact baseline and epoch, measured scope, current maturity gates, real commands or observations, new evidence, accepted changes, unresolved findings, cost and blockers, next action and checkpoint. Do not return only new plans when actual observation is possible. No-platform mode is a first-class acceptance path.

## Minimal local exercise

From this extracted kit: run `python tools/pep.py self-test`, then `python tools/pep.py summarize examples/executed-toy-loop/after`. To create an unaccepted scratch assessment, run `python tools/pep.py init-assessment --out /absolute/new/scratch --profile cli --subject-label my-subject`. It creates no product changes and grants no permissions. Bind real evidence before grading a real subject.
