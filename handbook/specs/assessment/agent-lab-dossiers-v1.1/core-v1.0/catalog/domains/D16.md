# D16 — Distribution and adoption

Status: authored candidate predicates. No product results or automatically qualified adapters are implied. Exact-duplicate checks do not establish semantic uniqueness; resolve cross-cutting overlaps when weighting an assignment.

## D16-P01 — Packaging and clean installation
Applicability trigger: distributable software.
Method: **DYNAMIC**. Install the actual built or released artifact into a clean consumer environment; inspect contents, startup and uninstall behavior.

- **PEP-16-01-01** — The package contains the files required for its promised capability.
- **PEP-16-01-02** — A clean consumer can install the selected artifact.
- **PEP-16-01-03** — Installation does not rely on the source repository being present.
- **PEP-16-01-04** — The installed version is discoverable.
- **PEP-16-01-05** — Required platform dependencies are detected with useful diagnostics.
- **PEP-16-01-06** — Installation avoids overwriting unrelated user files.
- **PEP-16-01-07** — The first installed smoke test exercises real product behavior.
- **PEP-16-01-08** — Uninstall removes owned resources without deleting unrelated data.
- **PEP-16-01-09** — Package metadata identifies the intended platform and runtime constraints.
- **PEP-16-01-10** — A successful package build is not reported as a successful clean installation.

Activation: use `templates/measurement-binding.template.json`. A catalog method is not a qualified instrument or a result.

## D16-P02 — Release and artifact acceptance
Applicability trigger: products producing versioned releases.
Method: **DYNAMIC**. Rebuild or inspect the release candidate, verify required checks and exercise the artifact promoted to the release channel.

- **PEP-16-02-01** — The release version identifies a distinct intended baseline.
- **PEP-16-02-02** — Required checks ran against the actual candidate artifact or its traceable source.
- **PEP-16-02-03** — Release notes distinguish shipped changes from planned work.
- **PEP-16-02-04** — The artifact digest matches the published or installed artifact.
- **PEP-16-02-05** — A release tag cannot substitute for missing build evidence.
- **PEP-16-02-06** — Promotion rules identify who or what may authorize publication.
- **PEP-16-02-07** — A failed mandatory gate blocks the affected release.
- **PEP-16-02-08** — Release rollback identifies a usable prior artifact.
- **PEP-16-02-09** — A release receipt identifies the actual publication destination.
- **PEP-16-02-10** — A source-level pass is not silently promoted to a release-level pass.

Activation: use `templates/measurement-binding.template.json`. A catalog method is not a qualified instrument or a result.

## D16-P03 — Deployment and runtime publication
Applicability trigger: products with hosted or service deployments.
Method: **DYNAMIC**. Deploy only within actual authority to a controlled target, verify routing and runtime behavior, and record honest blocked states for unavailable rights.

- **PEP-16-03-01** — The deployment target is distinguishable from a similarly named environment.
- **PEP-16-03-02** — Required runtime configuration is present without leaking secrets.
- **PEP-16-03-03** — The deployed artifact matches the intended release digest.
- **PEP-16-03-04** — Routing reaches the actual intended product surface.
- **PEP-16-03-05** — TLS or equivalent transport expectations are verified where applicable.
- **PEP-16-03-06** — Health and core-journey checks pass after deployment.
- **PEP-16-03-07** — A failed deployment leaves an observable status and recovery path.
- **PEP-16-03-08** — DNS or domain naming declarations are not treated as proof of live availability.
- **PEP-16-03-09** — Deployment logs identify the actual actor and target.
- **PEP-16-03-10** — Missing deployment authority does not block unrelated local verification.

## D16-P04 — Updates, compatibility and deprecation
Applicability trigger: products expected to evolve for installed consumers.
Method: **DYNAMIC**. Exercise supported update and downgrade paths with representative user state; test version skew and deprecation messaging.

- **PEP-16-04-01** — A supported installed version can update through the documented path.
- **PEP-16-04-02** — Updates preserve required user configuration and data.
- **PEP-16-04-03** — An update failure has a supported recovery path.
- **PEP-16-04-04** — Incompatible changes are communicated before the affected operation.
- **PEP-16-04-05** — Supported client-server version combinations are exercised.
- **PEP-16-04-06** — Deprecated interfaces expose their support and removal window.
- **PEP-16-04-07** — The product does not require an undocumented forced migration.
- **PEP-16-04-08** — A removed feature identifies affected consumers and alternatives.
- **PEP-16-04-09** — Update verification uses the installed artifact rather than only source tests.
- **PEP-16-04-10** — Rollback limitations are disclosed before a consequential update.

## D16-P05 — Documentation publication and discoverability
Applicability trigger: products publishing documentation or landing surfaces.
Method: **DYNAMIC**. Generate and access the actual published output using explicit content allowlists; follow routes and verify source-to-page identity.

- **PEP-16-05-01** — Published documentation identifies the product version it describes.
- **PEP-16-05-02** — Generated pages trace back to owner-held source documents.
- **PEP-16-05-03** — Private content is excluded by an explicit publication policy.
- **PEP-16-05-04** — Required navigation links resolve in the deployed route layout.
- **PEP-16-05-05** — Search results do not expose excluded private records.
- **PEP-16-05-06** — The landing page distinguishes a product, library, tool and conceptual project accurately.
- **PEP-16-05-07** — Documentation hosting does not become authoritative product state by accident.
- **PEP-16-05-08** — A docs build pass is distinguishable from successful publication.
- **PEP-16-05-09** — A changed source triggers a visible publication freshness state.
- **PEP-16-05-10** — Canonical routes preserve justified aliases until a tested cutover.

## D16-P06 — Adoption, support and consumer evidence
Applicability trigger: products intended for actual internal or external consumers.
Method: **OBSERVATIONAL**. Observe an authorized real consumer using the delivered artifact; retain support friction, outcomes and evidence labels.

- **PEP-16-06-01** — An actual consumer can find the correct supported entrypoint.
- **PEP-16-06-02** — Adoption evidence identifies the consumer and observation context appropriately.
- **PEP-16-06-03** — Internal dogfooding is labeled separately from external adoption.
- **PEP-16-06-04** — A support request has an identifiable intake and resolution path.
- **PEP-16-06-05** — Known limitations are discoverable before consequential use.
- **PEP-16-06-06** — Consumer-reported failures link to reproducible or explicitly unresolved findings.
- **PEP-16-06-07** — A claimed case study uses observed outcomes rather than invented testimonial text.
- **PEP-16-06-08** — Support burden is measured or explicitly estimated with uncertainty.
- **PEP-16-06-09** — The consumer can identify the version involved in a problem.
- **PEP-16-06-10** — Adoption claims do not count automated test invocations as independent customers.
