# D04 — Architecture and tradeoffs

Status: authored candidate predicates. No product results or automatically qualified adapters are implied. Exact-duplicate checks do not establish semantic uniqueness; resolve cross-cutting overlaps when weighting an assignment.

## D04-P01 — Boundaries and canonical ownership
Applicability trigger: multi-component or multi-repository subjects.
Method: **SEMANTIC**. Map responsibilities, state stores, consumer paths and changes; compare decomposition alternatives using actual coupling and ownership evidence.

- **PEP-04-01-01** — Each authoritative data object has one designated owner.
- **PEP-04-01-02** — Generated projections identify their source of truth.
- **PEP-04-01-03** — Tool implementation repositories do not own unrelated live portfolio state.
- **PEP-04-01-04** — Cross-component dependencies have documented direction.
- **PEP-04-01-05** — Duplicate implementations have a justified coexistence or consolidation decision.
- **PEP-04-01-06** — A repository split has a consumer or operational benefit beyond naming.
- **PEP-04-01-07** — Changes crossing boundaries identify integration responsibility.
- **PEP-04-01-08** — A boundary can be removed without losing unique historical evidence.
- **PEP-04-01-09** — Private deployment configuration is separated from generic tool source.
- **PEP-04-01-10** — An ownership dispute cannot be hidden by publishing a second authoritative record.

## D04-P02 — Interfaces and contracts
Applicability trigger: subjects exposing component boundaries.
Method: **DYNAMIC**. Exercise actual producers and consumers against versioned contracts, including malformed, older and partial messages.

- **PEP-04-02-01** — Required interface fields have explicit meanings.
- **PEP-04-02-02** — Producers emit data conforming to the selected contract version.
- **PEP-04-02-03** — Consumers reject invalid mandatory fields predictably.
- **PEP-04-02-04** — Unknown optional fields follow the declared compatibility rule.
- **PEP-04-02-05** — Error responses are distinguishable from successful empty results.
- **PEP-04-02-06** — Interface timeouts have documented observable behavior.
- **PEP-04-02-07** — Idempotency guarantees are exercised where duplicate requests are possible.
- **PEP-04-02-08** — Cancellation propagates across the intended interface boundary.
- **PEP-04-02-09** — A compatible older consumer is exercised when backward compatibility is promised.
- **PEP-04-02-10** — Contract drift between documentation and runtime behavior is detected.

## D04-P04 — Failure domains and resilience structure
Applicability trigger: subjects with interacting services, processes or devices.
Method: **DYNAMIC**. Inject isolated failures in disposable environments and observe propagation, containment, degradation and recovery across boundaries.

- **PEP-04-04-01** — A failed optional dependency does not disable unrelated mandatory capability.
- **PEP-04-04-02** — A hung worker cannot indefinitely monopolize shared capacity.
- **PEP-04-04-03** — Failure propagation matches the declared isolation boundary.
- **PEP-04-04-04** — Fallback behavior is distinguishable from full-function operation.
- **PEP-04-04-05** — Loss of network connectivity has a bounded local effect.
- **PEP-04-04-06** — A poison message cannot permanently block unrelated queue work.
- **PEP-04-04-07** — Recovery does not duplicate an already completed irreversible effect.
- **PEP-04-04-08** — Resource exhaustion in one tenant or project is contained as promised.
- **PEP-04-04-09** — Failure diagnostics identify the causal boundary rather than only a downstream symptom.
- **PEP-04-04-10** — The system can rejoin a recovered component without corrupting shared state.

## D04-P05 — Modifiability and evolutionary design
Applicability trigger: subjects expected to evolve.
Method: **SEMANTIC**. Walk concrete change scenarios through code, contracts, tests and consumers; measure the minimal affected surface and compare simpler designs.

- **PEP-04-05-01** — A representative feature change has a traceable impact set.
- **PEP-04-05-02** — A replaceable backend is not coupled through undocumented implementation details.
- **PEP-04-05-03** — Configuration changes avoid unnecessary rebuilds where runtime change is promised.
- **PEP-04-05-04** — Interface versioning permits the intended migration cadence.
- **PEP-04-05-05** — A domain rule has a designated implementation location.
- **PEP-04-05-06** — Architectural abstractions have actual consumers or a bounded validation plan.
- **PEP-04-05-07** — Circular dependencies have an explicit removal or containment strategy.
- **PEP-04-05-08** — Migration paths preserve required historical data and behavior.
- **PEP-04-05-09** — The design documents where a simpler solution was rejected and why.
- **PEP-04-05-10** — Architecture decisions have review triggers tied to changed assumptions.
