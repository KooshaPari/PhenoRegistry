## D09-P01 — Onboarding and first value
Applicability trigger: human-facing products.
Method: **DYNAMIC**. Use a clean intended-user account and representative starting state; follow the first-value path without developer-only shortcuts.

- **PEP-09-01-01** — A new intended user can identify the primary purpose.
- **PEP-09-01-02** — The first required action is distinguishable from optional exploration.
- **PEP-09-01-03** — Onboarding requests only information needed at that stage.
- **PEP-09-01-04** — The user can reach a real first-value outcome.
- **PEP-09-01-05** — Prerequisite failures are explained before the user reaches a dead end.
- **PEP-09-01-06** — Progress through multi-step onboarding is preserved as promised.
- **PEP-09-01-07** — The user can recover from an invalid onboarding input.
- **PEP-09-01-08** — Demo data is distinguishable from the user's actual data.
- **PEP-09-01-09** — An onboarding dismissal does not make required setup undiscoverable.
- **PEP-09-01-10** — The first-value journey has a measured completion result for the selected slice.

## D09-P04 — Loading, empty and failure states
Applicability trigger: interfaces with asynchronous or data-dependent behavior.
Method: **DYNAMIC**. Exercise empty, loading, partial, offline, permission-denied and failed states with controlled backend responses.

- **PEP-09-04-01** — Loading state is distinguishable from empty state.
- **PEP-09-04-02** — An empty result explains the next useful user action.
- **PEP-09-04-03** — Partial data is not presented as complete data.
- **PEP-09-04-04** — An offline state does not masquerade as a successful refresh.
- **PEP-09-04-05** — A failed operation provides a recoverable next step where one exists.
- **PEP-09-04-06** — A retry does not duplicate an already completed effect.
- **PEP-09-04-07** — Stale displayed data is identified when freshness matters.
- **PEP-09-04-08** — A denied operation does not reveal inaccessible resource details.
- **PEP-09-04-09** — Long-running operations expose meaningful progress or a bounded waiting state.
- **PEP-09-04-10** — Error messages do not erase recoverable user input.

## D09-P05 — Control, recovery and trust
Applicability trigger: products that change user state or perform consequential actions.
Method: **DYNAMIC**. Exercise undo, cancellation, confirmation, session expiry and permission changes; inspect what the user can understand and recover.

- **PEP-09-05-01** — The user can determine whether an operation actually completed.
- **PEP-09-05-02** — Undo restores the promised prior state for supported reversible actions.
- **PEP-09-05-03** — A canceled operation stops its future side effects within the declared boundary.
- **PEP-09-05-04** — Session expiry preserves recoverable work as promised.
- **PEP-09-05-05** — Permission changes take effect in the visible interaction state.
- **PEP-09-05-06** — Confirmation text identifies the real consequence rather than a generic warning.
- **PEP-09-05-07** — A background operation remains discoverable after leaving its initiating screen.
- **PEP-09-05-08** — The interface identifies simulations and conceptual demonstrations.
- **PEP-09-05-09** — The user can inspect or export a receipt for consequential completed work where required.
- **PEP-09-05-10** — A failed recovery does not claim the original state has been restored.
