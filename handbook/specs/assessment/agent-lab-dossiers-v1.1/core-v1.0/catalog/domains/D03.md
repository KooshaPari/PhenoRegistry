# D03 — Scope and capabilities

Status: authored candidate predicates. No product results or automatically qualified adapters are implied. Exact-duplicate checks do not establish semantic uniqueness; resolve cross-cutting overlaps when weighting an assignment.

## D03-P01 — Capability inventory
Applicability trigger: all subjects.
Method: **STRUCTURAL**. Enumerate actual entrypoints, exports, jobs, assets and dependencies using parsers and observed behavior; label inference and collection limits.

- **PEP-03-01-01** — The inventory identifies actual externally reachable entrypoints.
- **PEP-03-01-02** — Exported library interfaces are distinguished from internal helpers.
- **PEP-03-01-03** — Scheduled and background capabilities are included in the subject inventory.
- **PEP-03-01-04** — Experimental capabilities are labeled separately from supported capabilities.
- **PEP-03-01-05** — Capability existence claims identify their observation method.
- **PEP-03-01-06** — Undocumented implemented behavior is retained as a discovery.
- **PEP-03-01-07** — Declared but absent capabilities remain visible as gaps.
- **PEP-03-01-08** — Generated files are distinguishable from their authoritative inputs.
- **PEP-03-01-09** — Submodule and vendored boundaries are not silently merged into owned scope.
- **PEP-03-01-10** — The inventory declares inaccessible or uninspected subject areas.

## D03-P02 — Requirement quality
Applicability trigger: all assigned subjects.
Method: **SEMANTIC**. Review each requirement against its parent outcome, acceptance oracle and scope; use counterexamples to expose ambiguity or conjunction.

- **PEP-03-02-01** — Each accepted requirement has a stable identity and revision.
- **PEP-03-02-02** — The requirement specifies an observable result.
- **PEP-03-02-03** — Material ambiguous terms have operational definitions.
- **PEP-03-02-04** — Conjunctive requirements are split or intentionally treated as one indivisible outcome.
- **PEP-03-02-05** — The requirement identifies the beneficiary or consuming component.
- **PEP-03-02-06** — Acceptance conditions do not depend only on a preferred implementation detail.
- **PEP-03-02-07** — Requirement conflicts are exposed before release acceptance.
- **PEP-03-02-08** — Requirements have explicit applicability to the selected slice.
- **PEP-03-02-09** — The source of a requirement is distinguishable from its acceptance decision.
- **PEP-03-02-10** — A removed requirement retains a recorded disposition and affected consumers.

Activation: use `templates/measurement-binding.template.json`. A catalog method is not a qualified instrument or a result.

## D03-P03 — Journeys and user-slice completeness
Applicability trigger: subjects with user, operator or programmatic consumer journeys.
Method: **DYNAMIC**. Execute the bounded journey from a realistic starting state through its final effect, including recovery and verification by a consumer.

- **PEP-03-03-01** — The selected journey begins from the intended user's actual starting state.
- **PEP-03-03-02** — Required onboarding steps are included in journey scope.
- **PEP-03-03-03** — Every mandatory transition is executable through a supported interface.
- **PEP-03-03-04** — The final outcome is verified beyond an intermediate success message.
- **PEP-03-03-05** — A interrupted journey has an explicit continuation or recovery path.
- **PEP-03-03-06** — Required data survives the journey's supported restart boundary.
- **PEP-03-03-07** — The journey identifies the exact beneficiary slice being evaluated.
- **PEP-03-03-08** — Adjacent unsupported slices are not promoted by the tested slice.
- **PEP-03-03-09** — The journey includes relevant permission-denied behavior.
- **PEP-03-03-10** — Cross-repository dependencies are pinned consistently for the journey.

Activation: use `templates/measurement-binding.template.json`. A catalog method is not a qualified instrument or a result.

## D03-P04 — Applicability and scope selection
Applicability trigger: all assessments.
Method: **SEMANTIC**. Construct a capability-based applicability matrix; challenge both unjustified inclusion and convenient exclusions before freezing the epoch.

- **PEP-03-04-01** — All selected criteria have explicit applicability decisions or unresolved states.
- **PEP-03-04-02** — Non-applicability has a subject-specific reason.
- **PEP-03-04-03** — Product form alone does not exempt capability-created obligations.
- **PEP-03-04-04** — A new capability triggers review of related risk obligations.
- **PEP-03-04-05** — Missing evidence is not used as a reason to declare a criterion inapplicable.
- **PEP-03-04-06** — Scope weights are frozen before results are aggregated.
- **PEP-03-04-07** — An unreviewed exclusion cannot improve the verified score.
- **PEP-03-04-08** — Criteria outside the bounded assessment remain visible as unassessed catalog coverage.
- **PEP-03-04-09** — Mandatory parent obligations survive subdivision into smaller work packages.
- **PEP-03-04-10** — The assessment distinguishes a partial survey from a complete selected-scope assessment.

## D03-P05 — Open-world gap discovery
Applicability trigger: all products under discovery or reassessment.
Method: **SEMANTIC**. Compare declared, implemented, exercised and beneficial views; examine failures, implied obligations and credible alternatives within a finite frontier.

- **PEP-03-05-01** — Promised-but-absent behavior is classified as an implementation gap.
- **PEP-03-05-02** — Implemented-but-unverified behavior is classified as a verification gap.
- **PEP-03-05-03** — Capability-implied obligations are considered even when undocumented.
- **PEP-03-05-04** — Speculative enhancements are separated from accepted delivery debt.
- **PEP-03-05-05** — Unexpected behavior is checked for security or integrity consequences.
- **PEP-03-05-06** — Unused capabilities are evaluated for removal rather than automatic expansion.
- **PEP-03-05-07** — Failure and recovery paths are examined during discovery.
- **PEP-03-05-08** — Discovery records the frontier it did not inspect.
- **PEP-03-05-09** — Feature parity with competitors is not treated as an automatic obligation.
- **PEP-03-05-10** — Each material gap identifies the kind of action needed to resolve it.

Activation: use `templates/measurement-binding.template.json`. A catalog method is not a qualified instrument or a result.

## D03-P06 — Delivery decomposition and backlog quality
Applicability trigger: subjects with planned or active work.
Method: **SEMANTIC**. Trace work packages to accepted outcomes and dependencies; compare completion evidence with parent obligations and integration boundaries.

- **PEP-03-06-01** — Each work item resolves an identified obligation or experiment.
- **PEP-03-06-02** — Work acceptance includes a demonstrable outcome rather than document production alone.
- **PEP-03-06-03** — Dependencies distinguish true blockers from optional improvements.
- **PEP-03-06-04** — A work item names the actual owning repository or component.
- **PEP-03-06-05** — Split tasks preserve responsibility for inherited defects.
- **PEP-03-06-06** — A task cannot close its parent outcome solely by closing its own narrow scope.
- **PEP-03-06-07** — The backlog separates proposed opportunities from committed work.
- **PEP-03-06-08** — Blocked work names the next action and wakeup condition.
- **PEP-03-06-09** — The work package fits the remaining resource envelope.
- **PEP-03-06-10** — The plan contains an end-to-end integration step for independently delivered components.
