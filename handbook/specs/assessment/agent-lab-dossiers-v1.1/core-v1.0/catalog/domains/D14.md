# D14 — Security and trust

## D14-P01 — Threat model and trust boundaries
Applicability trigger: subjects with security-relevant capabilities.
Method: **SEMANTIC**. Map assets, actors, entrypoints and trust boundaries; derive plausible misuse cases and challenge assumptions with authorized tests.

- **PEP-14-01-01** — Sensitive assets are identified for the selected product slice.
- **PEP-14-01-02** — External and internal trust boundaries are distinguishable.
- **PEP-14-01-03** — Threat actors are matched to actual exposure and capabilities.
- **PEP-14-01-04** — Abuse cases include misuse of legitimate authenticated access.
- **PEP-14-01-05** — Agent-readable untrusted content is identified as a potential instruction-injection surface.
- **PEP-14-01-06** — Security assumptions identify the controls on which they depend.
- **PEP-14-01-07** — Threat mitigations map to testable obligations.
- **PEP-14-01-08** — Residual risks have explicit owners or acceptance decisions.
- **PEP-14-01-09** — New entrypoints trigger a threat-model review.
- **PEP-14-01-10** — A threat-model document alone is not treated as proof of implemented protection.

## D14-P02 — Authentication and session security
Applicability trigger: subjects with identities or sessions.
Method: **DYNAMIC**. Use synthetic accounts to exercise valid, invalid, expired, revoked and replayed credentials against actual authentication boundaries.

- **PEP-14-02-01** — Invalid credentials cannot create an authenticated session.
- **PEP-14-02-02** — Expired credentials are rejected according to the session policy.
- **PEP-14-02-03** — Revoked credentials cease to authorize protected operations.
- **PEP-14-02-04** — Session identifiers are not exposed through unnecessary public channels.
- **PEP-14-02-05** — Logout invalidates the promised session scope.
- **PEP-14-02-06** — Authentication failures do not reveal sensitive account details beyond policy.
- **PEP-14-02-07** — Credential rotation preserves intended access without accepting obsolete secrets indefinitely.
- **PEP-14-02-08** — Session fixation or replay is evaluated against the actual threat model.
- **PEP-14-02-09** — Optional authentication absence cannot silently expose a protected production path.
- **PEP-14-02-10** — Authentication test evidence uses the real selected identity boundary rather than mocks alone.

## D14-P03 — Authorization and tenant isolation
Applicability trigger: subjects controlling access to resources or actions.
Method: **DYNAMIC**. Exercise a permission matrix with synthetic principals across direct, indirect and cross-tenant resource paths.

- **PEP-14-03-01** — Protected operations verify the caller's permission at the actual enforcement boundary.
- **PEP-14-03-02** — Resource ownership is checked for direct identifier access.
- **PEP-14-03-03** — A lower-privilege user cannot invoke a higher-privilege action through an alternate route.
- **PEP-14-03-04** — Cross-tenant reads are denied where tenant isolation is required.
- **PEP-14-03-05** — Cross-tenant writes are denied where tenant isolation is required.
- **PEP-14-03-06** — Permission revocation takes effect within the accepted window.
- **PEP-14-03-07** — Background jobs preserve the initiating authorization scope.
- **PEP-14-03-08** — Cached authorization does not outlive its declared validity.
- **PEP-14-03-09** — A denied operation leaves protected state unchanged.
- **PEP-14-03-10** — An agent-authored policy cannot grant host capabilities unavailable to its authority source.

Applicability trigger: subjects using credentials or sensitive configuration.
Method: **DYNAMIC**. Use synthetic secrets to inspect storage, logs, process arguments, artifacts and redaction paths under success and failure.

- **PEP-14-04-01** — Required secrets are not committed to ordinary source history.
- **PEP-14-04-02** — Secret-like content in new changes is checked through the selected detection path.

- **PEP-14-04-09** — A missing secret remains an authority or environment blocker rather than a fake pass.
- **PEP-14-04-10** — Sensitive captures remain within their authorized evidence store.

Applicability trigger: subjects processing untrusted inputs or dependencies.
Method: **DYNAMIC**. Run authorized malformed and adversarial fixtures against exposed boundaries; inspect containment and meaningful failure detection.

- **PEP-14-05-01** — Untrusted input cannot escape its intended command or query interpretation.
- **PEP-14-05-02** — Filesystem paths are constrained to the authorized root where required.
- **PEP-14-05-03** — Oversized inputs have bounded rejection behavior.
- **PEP-14-05-04** — Malformed serialized data is rejected without corrupting accepted state.
- **PEP-14-05-05** — Deserialization does not instantiate unintended executable behavior.
- **PEP-14-05-06** — Untrusted URLs cannot access forbidden internal resources through the product.
- **PEP-14-05-07** — Archive extraction cannot write outside the intended destination.
- **PEP-14-05-08** — Dependency vulnerability findings identify the affected resolved version.
- **PEP-14-05-09** — A mitigation is verified through the relevant reachable behavior.
- **PEP-14-05-10** — Security tests do not use production victims or unapproved destructive payloads.

## D14-P06 — Supply chain, releases and security governance
Applicability trigger: subjects distributing software or consuming executable artifacts.
Method: **STRUCTURAL**. Trace release artifacts through source, build and publication records; verify selected signatures and security workflows against actual receipts.

- **PEP-14-06-01** — A distributed artifact maps to its actual source revision.
- **PEP-14-06-02** — Build provenance identifies material inputs and the producing environment.
- **PEP-14-06-03** — Artifact verification checks the expected identity rather than any valid signature.
- **PEP-14-06-04** — Dependency and license inventory describes the distributed artifact scope.
- **PEP-14-06-05** — Required release security checks executed on the actual release baseline.
- **PEP-14-06-06** — A failed security gate cannot be silently marked successful by report editing.
- **PEP-14-06-07** — Vulnerability disclosures have an authorized intake and response path.
- **PEP-14-06-08** — Security exceptions identify scope, rationale and review date.
- **PEP-14-06-09** — Publication credentials are separated from untrusted build execution where required.
- **PEP-14-06-10** — A provenance receipt is not treated as proof that the product is correct or secure.
